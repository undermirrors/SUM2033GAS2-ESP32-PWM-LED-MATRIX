# Dalle 32x32 four-scan à SUM2030GAS2 : diagnostic et correctif

## Le symptôme

Avec `Sum2033Display(32, 32, /*fourScan=*/true, 1)` :

- seuls les pixels dont `y % 8 < 4` apparaissent ;
- chaque pixel affiché apparaît une deuxième fois, 4 lignes plus loin.

## Ce qui se passe (hypothèse)

Le mapping four-scan de `flip()` envoie la ligne `y` du canvas sur l'adresse
de ligne `y % 8` (A/B/C, 8 adresses, `scan = 8`). Le symptôme veut donc dire :

- seules les données des adresses 0 à 3 s'affichent ;
- chacune s'affiche aussi sur l'adresse +4.

Le SUM2030 garde les lignes en SRAM et les rejoue lui-même. Ici, il se comporte
comme s'il croyait n'avoir que 4 lignes à balayer au lieu de 8.

Le nombre de lignes lui est donné par le champ « scan » du registre REG2
(bits 6 à 10). La lib, écrite pour le SUM2033, y met `scan - 1 = 7`. Or ce
champ n'a été vérifié qu'en 1/32 scan, où tous les bits sont à 1 et où sa
position exacte ne change donc rien. Le SUM2030 (1/16 scan maximum, champ
probablement sur 4 bits) le lit sans doute un bit plus haut : `7 << 6` lu à
partir du bit 7 donne 3, soit 4 lignes. C'est exactement le symptôme.

Les essais faits jusqu'ici (1/8, 1/16, taille du panneau, etc.) changeaient
toujours la géométrie **et** ce registre en même temps, ce qui empêchait de
les distinguer. La lib permet maintenant de régler ce champ seul.

> Pas de carte des registres dans la datasheet (une seule page), donc c'est à
> confirmer sur la dalle. C'est le but du sketch `src/main.cpp`.

## Procédure

Si tu appliques seulement `SUM2030-lib.patch` à ton dépôt, sauvegarde ton
`src/main.cpp`, puis copie le `src/main.cpp` de ce dossier à sa place le temps
du diagnostic.

1. Flasher (`pio run -t upload`), puis ouvrir le moniteur série
   (`pio device monitor`, 115200 bauds, `h` pour l'aide).
2. Au démarrage, `scanField = 15` (l'hypothèse) et la mire **a 7** :
   toute l'adresse de ligne 7 est allumée, R1 en rouge et R2 en bleu. Cette
   mire ne dépend pas de l'ordre des pixels dans la chaîne.
   - **Bon** : exactement 4 lignes physiques allumées, 2 rouges en haut et 2
     bleues en bas.
   - **Mauvais** : 8 lignes (l'adresse est doublée), ou rien du tout.
   - Pour revoir le bug d'origine : `s -1` (= 7).
3. Si 15 ne donne pas 4 lignes, taper `sweep`. Ça essaie toutes les valeurs
   de 0 à 31, 4 s chacune, sur la mire `a 7`, et affiche la valeur courante
   dans le moniteur. Noter celle(s) qui allument exactement 4 lignes, puis la
   fixer avec `s <valeur>`.
4. Avec la bonne valeur, passer en revue `a 0` à `a 7`. Chaque adresse doit
   allumer 4 lignes, jamais les mêmes d'une adresse à l'autre, et à elles 8
   elles doivent couvrir les 32 lignes.
5. `stairs` : chaque adresse `a` allume une barre de `4 × (a + 1)` pixels. Si le
   mapping par défaut est le bon, on voit 4 blocs de 8 lignes, chacun un
   escalier complet de 4 à 32 px. Si le mapping diffère, les barres peuvent
   être coupées en morceaux ou partir de la droite. Ce n'est pas un problème
   de registre, voir plus bas. Il faut juste 8 longueurs différentes par
   couleur, sans motif qui se répète toutes les 4 lignes.
6. Vérifier le résultat final avec `canvas`. On doit voir un cadre, une
   diagonale du coin haut-gauche au coin bas-droite, des coins rouge
   (haut-gauche), vert (haut-droite), bleu (bas-gauche) et jaune (bas-droite),
   et « OK » au milieu.
7. Reporter la valeur trouvée dans le vrai sketch :

   ```cpp
   cfg.scanField = 15;   // ou la valeur trouvée avec sweep
   ```

## Si `a 0..7` est bon mais que `canvas` est mélangé

Alors le registre est bon, mais l'ordre des pixels dans la chaîne n'est pas
celui de `FOUR_SCAN_32PX_HIGH`. La mire stairs donne déjà l'essentiel :

| couleur | lignes de données | moitié du flux DMA d'un panneau |
|---|---|---|
| rouge | R1 (haut) | 1re (pixels 0..31 envoyés) |
| vert | R1 (haut) | 2e (pixels 32..63) |
| bleu | R2 (bas) | 1re |
| blanc | R2 (bas) | 2e |

Avec le mapping par défaut, on attend de haut en bas : vert (lignes 0 à 7),
rouge (8 à 15), blanc (16 à 23), bleu (24 à 31). Les barres doivent pousser
depuis la gauche.

Pour le détail, le mode `walk` allume un seul pixel DMA à la fois (Entrée pour
avancer, `w <x> <y>` pour sauter), et affiche son adresse et l'endroit où le
mapping par défaut croit qu'il est. Avec le vrai mapping relevé, on écrit une
fonction et on la passe à la lib :

```cpp
// dx = 0..63 (ordre d'envoi), dy = 0..15 (dy < 8 : R1 adresse dy, sinon R2 adresse dy-8)
static bool monMapping(int dx, int dy, int panelW, int scan, int& x, int& y) {
  // ... calculer (x, y) dans le panneau 32x32
  return true;
}
display.setFourScanMap(monMapping);
```

## Autres commandes du sketch

- `b <0..63>` : luminosité globale.
- `r1|r2|r3 <valeur>` : valeur brute d'un registre (`0x....`), `-1` pour revenir
  à la valeur calculée. Utile si un autre champ (profondeur de couleur…) se
  révélait aussi décalé.
- `h` : aide et valeurs actuelles des registres.

## Ce qui a changé dans la lib

- `Sum2033Config::scanField` (-1 = `scan - 1`, comportement d'origine) et
  `reg1Override` / `reg2Override` / `reg3Override`.
- `Sum2033::setScanField()`, `setRegOverride()` et `regValue()` pour les
  changer à chaud. Ils s'appliquent à la frame suivante, sans redémarrer le DMA.
- `Sum2033Display::setFourScanMap()` pour remplacer le mapping four-scan.
- Avec les valeurs par défaut, le flux envoyé est identique octet pour octet à
  l'ancienne version (vérifié sur PC). `test/host/protocol_test.cpp` couvre les
  nouveaux réglages.
- L'ancien `src/main.cpp` (WebSocket) est dans `examples/websocket/`.
